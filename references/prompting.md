# Prompt 组织规范

这份文档讲怎么把一个"帮我配张图"的模糊需求，变成一个能生成出贴合项目效果的详细 prompt。核心原则：**prompt 的质量几乎完全决定生成效果**，用户丢一句话过来，不代表你应该原样把这句话丢给生图 API——你的工作是把这句话背后没说出来的信息补全。

## 为什么要这么讲究

用户明确要求生成效果必须"适配项目"，而不是随便一张漂亮但风格突兀的图。一张图放进项目里违和，比没有这张图更糟——因为它意味着又要花一次生成成本、还要占用一轮沟通去改。所以生成之前多想两步，比生成之后返工划算得多。

## 第一步：先搞清楚这张图在项目里扮演什么角色

在动笔组织 prompt 之前，先确认(能从上下文推断的就推断，推断不出来的问一句)：

- **用途**：这张图具体放在项目哪个位置？首页 hero、某个功能的图标、文章配图、空状态占位图……不同用途对构图、留白、宽高比的要求完全不同(hero 图通常要给文案留出安全区，图标要在小尺寸下依然清晰，这些是生图 API 不会自己想到的)。
- **项目已有的视觉语言**：项目里如果已经有 CSS 变量定义的主题色、已有的其他图片素材、字体气质，去看一眼，把这些实际信息(具体色值、整体调性)写进 prompt 里，而不是凭感觉编一个"现代简约风"——生成图和项目其他部分脱节，是最常见的翻车原因。没有已有素材可参考的全新项目，可以跟用户确认期望的调性。
- **尺寸/比例**：由用途反推，比如首页 hero 通常是宽幅、图标接近方形、文章配图看内文排版。具体数值要落到对应 provider 支持的取值范围(见 `provider-params.md`)。

## 第二步：用结构化骨架把 prompt 写完整

不要把用户一句话的描述直接透传给 API。按下面这个骨架逐项填完，缺的维度自己合理补充(不要瞎编跟需求无关的内容，只补充跟已知信息一致、能让画面更明确的细节)：

```
用途: <这张图在项目里的具体使用场景，决定构图/尺寸>
主体: <画面主体是什么，动作/姿态/表情等关键细节>
风格/媒介: <插画/摄影/3D渲染/扁平设计等，要呼应项目调性>
构图: <整体构图、留白需求，比如"右侧留白供文案叠加">
色彩: <是否要贴合项目主题色，给出具体色调或色值>
氛围/光线: <情绪基调，比如温暖/冷静/活泼>
文字(如有): <图片里如果需要出现文字，逐字精确列出，不要意译>
约束: <必须保留的元素/必须避免的元素，比如"不要水印""不要出现真实品牌 logo">
```

**全部用中文写**——这是用户明确要求的，方便审阅，不要擅自换成英文。

## 第三步：生成前必须给用户看

不管多有把握，正式调用 API 之前，把组织好的完整 prompt(以及准备用哪个 provider、尺寸等关键参数)完整地展示给用户，等待确认或修改意见后再生成。这是强制步骤，原因很直接：生成是要花钱的，而且改一次 prompt 比生成后返工便宜得多。具体交互方式见 `SKILL.md` 的工作流程部分。

## 常见坑

- **文字渲染不准**：生图模型对图片内嵌文字的准确度普遍有限，如果这张图必须精确显示某几个字，要在 prompt 里逐字标注，并且生成后要检查文字是否正确，不对就重新生成或去掉文字需求(改用后期叠字的方案)，不要将就。
- **主体细节漂移**：如果是针对同一主体做多次生成/微调(比如换个姿势但保持同一只猫的花纹)，每次都要把关键不变量重复写进 prompt(比如"黑白奶牛花纹，不要变成其他花色")，不要假设模型会"记住"上一轮的设定。
- **风格词汇空洞**：像"高级感""有质感"这种词汇对生图模型帮助有限，尽量换成具体、可描述的视觉特征(材质、光影方向、色彩饱和度、构图疏密)。
